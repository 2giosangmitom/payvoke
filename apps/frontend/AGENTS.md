# Payvoke frontend — agent instructions

Scope: `apps/frontend/**`. Follow this file when implementing or reviewing any frontend change. Inspect the existing implementation and the affected route before editing. Preserve the Payvoke identity and working auth, API and marketplace flows.

## Product and stack

Payvoke is a marketplace for discovering AI agents/tools, saving starred listings into collections, and managing provider apps, keys, drafts and publications. The UI is currently a marketplace preview; do not imply that paid execution, streaming chat or settlements work until backend endpoints exist.

- Framework: **TanStack Start + TanStack Router**, file-based routing, React 19, TypeScript.
- Data fetching/caching: **TanStack Query** over the typed **Hono RPC** client in `src/lib/api/client.ts`; each feature wraps its endpoints in `src/features/<feature>/api.ts`.
- Document head: **unhead** (`@unhead/react`), set up in `src/app/head.ts` and rendered on the server by `src/server.ts`.
- UI foundation: **shadcn/ui** components sourced into `src/components/ui/`, **Base UI**, Tailwind v4, CSS theme tokens in `src/global.css`.
- Wallet: wagmi/viem, better-auth SIWE. Preserve Avalanche Fuji wallet flow.
- Motion: React Bits for targeted marketing effects; `motion/react` already exists for custom transitions.
- Chat/AI UI: **assistant-ui** when an actual thread, chat, agent run or tool-call interface is implemented.
- Icons: lucide-react, and `@web3icons/react` for chain/wallet marks.

## Routing, layouts and document ownership

**Use TanStack Router layout routes. Do not duplicate shared chrome inside pages.**

Current route map:

| URL                                   | Route file                                 | Responsibility                                                                                                                                                        |
| ------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (pathless)                            | `src/routes/_market.tsx`                   | Public site chrome: marketing header (Home, Store, Docs, Console) + footer                                                                                            |
| `/`                                   | `src/routes/_market.index.tsx`             | Landing page                                                                                                                                                          |
| `/store`, `/store/$appId`             | `src/routes/_market.store.*.tsx`           | Public directory and app detail; CTA opens a chat thread with the app                                                                                                 |
| `/docs`, `/docs/$section`             | `src/routes/_market.docs*.tsx`             | Builder API reference rendered from `src/features/docs/openapi.json`, generated by `bun --filter api docs` (never edit it)                                            |
| `/console`                            | `src/routes/console.tsx`                   | Signed-in app shell (`ConsoleShell`): icon rail (bottom bar on phones), breadcrumb, sign-in gate                                                                      |
| `/console/`                           | `src/routes/console.index.tsx`             | Console home: jobs that need the buyer, money in flight, running work, recent chats                                                                                   |
| `/console/chat/...`                   | `src/routes/console.chat*.tsx`             | Every app: thread list + `ThreadChat` (assistant-ui thread over the API timeline)                                                                                     |
| `/console/activity`                   | `src/routes/console.activity.tsx`          | Every paid invocation with hold state and next deadline                                                                                                               |
| `/console/wallet`                     | `src/routes/console.wallet.tsx`            | USDC in the wallet, in the vault and held for jobs; deposit/withdraw, earnings, one-click pay keys                                                                    |
| `/console/keys`                       | `src/routes/console.keys.tsx`              | API keys (MCP access tokens, each with an optional autopay limit) and the guide to connect an agent harness; agent keys live in Studio (`/console/connect` redirects) |
| `/console/approve/$quoteId`           | `src/routes/console.approve.$quoteId.tsx`  | Approval link from MCP `request_payment`: the buyer reviews and pays a coding agent's quote                                                                           |
| `/console/studio/...`                 | `src/routes/console.studio.*.tsx`          | Provider Studio: app info, keys; commands are read-only (bots register them via API)                                                                                  |
| `/chat`, `/dashboard`, `/app`, `/run` | `src/routes/{chat,dashboard,app,run}*.tsx` | Redirects from old URLs into the console                                                                                                                              |
| (document)                            | `src/routes/__root.tsx`                    | `<html>`, unhead provider and document tags, `HeadContent`, providers, `<Outlet>`, `Scripts`                                                                          |

- Public, browse-only pages are children of `_market`; anything signed-in (chat, runs, payments, Studio) is a child of `console`. Do not put marketing chrome around working surfaces.
- Use a new pathless layout for a distinct shell (for example a future immersive chat surface) instead of sprinkling `pathname` conditionals through every page. Keep layout concerns in the parent and page concerns in the child.
- Nested pages must render through `<Outlet />`. Share nav, account controls, page width and other repeated chrome in layouts/components. Each page owns its `<main>` and its own content hierarchy.
- Use `createFileRoute`, typed `Link`, `useNavigate`, and typed route search validation. Use router links for internal navigation; anchor links for external URLs and same-page hashes.
- Head tags go through unhead, never the route `head` option. Declare a page's title and description as route `staticData: { title, description }`; the root applies the deepest match, so it holds even behind the console sign-in gate. A component that loads a better title (an app or thread name) calls `usePageMeta()` from `src/app/head.ts`. Document-wide tags (charset, viewport, icon, font preloads) live in `useDocumentHead()`.
- **Never hand-edit `src/routeTree.gen.ts`.** It is generated by the TanStack Start Vite plugin. Regenerate through the build/dev process after renaming route files.
- TanStack Start is isomorphic. Loaders can run on server and client; use Start `createServerFn` for server-only work. Do not access browser globals during SSR render or from loaders. Do not use React hooks inside route `loader`/`beforeLoad`.
- A client-side auth gate is useful UX, but backend authorization must still be checked on every private API action. Do not rely on hiding a link to protect data.

## Visual language and component selection

Current design direction: **Osaka Jade / dark editorial terminal**, not generic dashboard chrome. Theme lives under `[data-theme="osaka-jade"]` in `src/global.css`.

- Palette: deep charcoal green backgrounds (`--t-bg`, `--t-bg-deep`), jade (`--t-brand`), warm ivory text (`--t-text`), olive-gray secondary text, quiet green borders. Use tokens instead of one-off hex values.
- Type: Geist Variable for display/editorial headlines and all console text; JetBrains Mono Variable for amounts, counts, times, IDs, keys and code only. Console labels are sentence case at 12px or larger: no tiny tracked uppercase labels.
- Console (data terminal): colour goes on data and status, not chrome. The one selection mark everywhere (rail item, filter, run stage) is a 1px jade line exactly as wide as its target. Status pills are pale tints; figures are right-aligned tabular mono with the unit in grey; no entrance animations on work screens.
- Layout: spacious but purposeful; grid/list views for listings, legible form groupings, clear primary action. Keep square corners and restrained borders; `--radius` is intentionally `0px`.
- Interaction: clear hover/focus/disabled/loading/error/success states. Motion supports comprehension, never gates an action. Respect `prefers-reduced-motion`.
- Keep logo, favicon, wordmark and header consistent via `/logo.svg`. Avoid invented logos, gradients, glass panels, repetitive icon cards and template filler.
- Mobile layouts must work at 320px and across tablet/desktop breakpoints. No horizontal overflow from long keys, addresses, tables or code.

**Default to shadcn/ui for product controls**: Button, Input, Textarea, Label/Field, Select, Tabs, Dialog, Sheet, DropdownMenu, Tooltip, Badge, Skeleton, Alert, Table, ScrollArea and other common primitives. Use the existing versions in `src/components/ui/` first. Use `Button`/`Input`/`Tabs` already installed rather than making new click/keyboard behavior from scratch.

- shadcn is _owned source_, not a black-box dependency. Adapt its local component classes to the Payvoke tokens and keyboard/a11y requirements; keep its primitive behavior intact. This project uses **Base UI** variants, so do not paste Radix-specific imports into those files. Use `ToggleGroup` for one-of-N filters and `Tabs` for views with associated tab panels.
- To find a component, use the shadcn MCP registry tools when available (search, inspect example, get add command), or use the existing local shadcn CLI. `components.json` is the source of truth for aliases, registry and styling. Example: from `apps/frontend`, `bunx shadcn add input tabs --yes`.
- Prefer a small domain component composed from shadcn primitives over a large custom bespoke input/modal. Keep domain components outside `components/ui/`; reserve `ui/` for generic primitives and visual effect building blocks.
- Do not introduce a second design system (MUI, Ant, Chakra, etc.) or style native controls differently on every route.

## AI, assistant-ui and agent conversation interfaces

Use **assistant-ui** for actual chats, model messages, tool calls, runs and conversation history. Keep it dedicated to chat surfaces; ordinary marketplace search, provider forms and collections remain shadcn UI.

How the chat is built (`src/features/chat/`):

- `use-timeline.ts` reads `GET /v1/threads/:id/timeline` and keeps it live over `GET /v1/threads/:id/events`: each `timeline` event replaces the cached projection, `delta` events append streamed text to one part. Never stitch API tables together in the browser.
- `thread-runtime.ts` converts timeline messages for `useExternalStoreRuntime`, uploads attachments through `ThreadAttachmentAdapter`, and provides `ThreadChatContext` (tool status and results by id, `submitTool`, `acceptOffer`).
- Every interactive or structured piece is a tool-call part rendered by `tool-uis.tsx`: `ask_form` (ElicitationForm + `SchemaForm`), `ask_choice` (OptionList), `confirm` and `offer` (ApprovalCard), `command`, `progress` (one AgentPlan via `MessagePrimitive.GroupedParts`), `render_ui` (OpenUI), `revision`, `result`. Results go to `POST /v1/threads/:id/tool-results`.
- A paid run is one assistant message (`run-message.tsx`): the run strip, the payment step while one is owed, then its parts. Audio plays in the waveform `AudioPlayer` (`components/assistant-ui/elements/media-player.tsx`), drawn from the peaks the uploader measured (`files.ts` decodes local audio before upload).
- assistant-ui registry components live in `src/components/assistant-ui/elements/` as owned source, restyled through `surfaces.tsx` (square corners, jade tokens). When adding more with `bunx shadcn add @assistant-ui/...`, keep the project's own `ui/button`, `tooltip`, `badge` and `dialog` instead of the overwrites the registry proposes.

- First inspect the backend conversation/run API and authentication. No mock messages presented as real agent output and no fake streaming. Add UI only against an explicit contract or a clearly labeled demo.
- Build the chat shell using assistant-ui's thread/message/composer and tool-call primitives, then theme them to Payvoke's design tokens. Keep accessibility, keyboard send behavior, scroll anchoring and long-output handling.
- Separate server transport (streaming protocol, authentication, run IDs, cancellation, retry) from assistant-ui rendering. The server owns API keys, provider credentials and settlement-sensitive state; never ship secrets or private provider tokens to the browser.
- Handle first-load history, sending, partial streaming, tool status, errors, retry, abort and disconnected states explicitly. Do not silently drop messages if a stream fails.
- Use a route/layout appropriate for focused chat work. Tie thread identifiers to route params/search when deep links or reloads need to preserve context.
- Add dependencies and assistant-ui shadcn registry components only when building the chat feature. Check currently installed package versions and generated component APIs before using examples. No speculative dependency installs just for a placeholder.

## React Bits and presentation effects

Use **React Bits** on the landing page and a few high-impact marketing moments when the effect clarifies the product or adds distinctive polish. Existing `src/components/BlurText.tsx` is available and used for a restrained landing micro-animation. Other custom hero effects are in `src/components/ui/`.

- Fetch candidate components through the `@react-bits` registry configured in `components.json`, inspect their API and dependencies, then adapt to current colors, fonts and motion levels.
- Keep effects behind small components and out of form controls, account settings, data tables, credential displays and essential text paths.
- Prefer GPU-friendly transforms and opacity. Avoid perpetual canvas work behind dashboard content; ensure cleanup for observers, timers and RAF loops.
- Provide a stable static presentation for reduced motion, touch interfaces and environments without canvas. Meaningful content must remain accessible as text.
- The landing must still load and be usable without effects. Avoid a proliferation of competing animations.

## Data, caches and application state

- Call the API only through the RPC client: `call(client.v1....$get(...))` returns the typed body or throws `ApiError` with the API's public code. Put each endpoint wrapper in its feature's `api.ts` and derive response types with `Body<typeof client....>` instead of redeclaring them. Use `callAs<T>()` only for bodies the API serializes from stored JSON (signed quote documents, AG-UI snapshots). Never build API URLs by hand; use `$url()` for EventSource.
- Use TanStack Query for server state. Query keys include all meaningful dimensions: `['catalog', kind, query]`, `['account', accountId, 'stars']`, `['account', accountId, 'collections']`, and app-scoped product/key keys. Keep anonymous data separate from account data.
- Use `useInfiniteQuery` for cursor pagination; preserve the cursor and load-more UX. Avoid local `useEffect` fetching for data that Query can cache/dedupe.
- Set explicit sensible stale/cache lifetimes; invalidate relevant keys after successful mutations. On sign-out or account switch, remove account-scoped cache to prevent cross-wallet leakage. Don't cache one-time API key secrets.
- Model pending, loading, empty, error and retry states. Preserve actionable server messages without leaking credentials or raw stack traces.
- Use route search params for shareable search/filters when adding substantial filter state; validate params at the route boundary. Transient form input and dialog open state can remain local.
- Do not optimistically present a mutation as successful unless rollback and error behavior are defined.

## Security, wallet and backend boundaries

- Existing wallet sign-in uses SIWE and Avalanche Fuji via `wallet-access.tsx`. Reuse it; do not add competing wallet connect UI or duplicate auth context.
- Browser code must not receive provider API secrets, server signing keys, database URLs or privileged tokens. Provider API keys are shown **once** only upon creation/rotation, then stored server-side as configured by the backend.
- Never persist a raw provider key to localStorage, TanStack Query or analytics; do not print it in logs. Provide explicit copy UI and clear one-time display.
- Route-level guards complement backend checks. Do not build authorization based on front-end role assumptions.
- Use the shared RPC `client` with its existing credential policy; do not silently change request authentication/CORS rules.
- API error handling must distinguish authentication, validation, network and server failure where the server contract allows it.

## Accessibility, quality and testing

- HTML semantics first: one `<main>` per page, heading hierarchy, labeled form fields, real links for navigation, real buttons for actions, accessible dialogs and tabs. Don't replace keyboard interactions with pointer-only handlers.
- Every input needs a visible label or specific accessible name. Icon-only buttons require `aria-label`. Announce mutation errors using `role="alert"`; maintain visible focus states.
- Validate contrast and text wrapping with the actual jade/dark theme. Check long names, empty lists, credentials, mobile navigation and reduced motion.
- For route/layout changes, validate a direct load and client navigation on `/`, `/agents`, `/app`, then verify anonymous and authenticated header behavior.
- Run `bun run --cwd apps/frontend build`, `bun run --cwd apps/frontend typecheck` and `bun run --cwd apps/frontend test` before handoff. Root formatting/lint commands: `bunx oxfmt` and `bunx oxlint` (scope to touched files where practical). Don't format the generated route tree.
- If a change requires a backend endpoint, verify its contract before wiring UI. Don't misrepresent an unimplemented capability as live.

## File organization and change discipline

| Path                      | Purpose                                                                                |
| ------------------------- | -------------------------------------------------------------------------------------- |
| `src/routes/`             | Thin router entrypoints: layouts, params, `staticData` page meta                       |
| `src/features/<feature>/` | One product area: its components, `api.ts` endpoint wrappers and helpers               |
| `src/components/layout/`  | Site chrome, page kit and theme switch shared by every feature                         |
| `src/components/ui/`      | shadcn primitives and isolated generic visual effects                                  |
| `src/app/`                | App-wide providers and unhead setup                                                    |
| `src/lib/`                | RPC client, theme and generic helpers with no feature knowledge                        |
| `src/server.ts`           | Start server entry: renders each page and writes unhead's tags into it                 |
| `src/global.css`          | Design tokens and project-level styles; don't create inconsistent page-specific themes |
| `components.json`         | shadcn registry, aliases, style settings                                               |

Features: `auth` (wallet sign-in), `apps` (catalog and Studio endpoints, command card, price formatting), `store`, `studio`, `chat`, `payments` (quotes, grant checks, signed submission), `activity`, `wallet`, `keys`, `console` (shell and home), `landing`. A feature may import another feature's `api.ts` or components; anything two features both need and that has no domain meaning belongs in `components/` or `lib/`.

When modifying existing code, preserve unfinished work in the worktree. Prefer cohesive, narrow changes; avoid incidental redesigns of unrelated pages. Keep reusable styles and components aligned with the established system, remove dead imports, and report what was actually built versus what remains planned.
